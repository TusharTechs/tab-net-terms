# Full demo run with Visa (2026-11-10, run `rmwaklnvk`)

`LIVE_VIC=1 npx tsx scripts/demo-run.ts` plays all nine scenes into `data/desk-demo.json`; the demo screen (`npm run screen`) streams them. Live: Metal testnet, Claude (`claude-opus-5-5`, buyer agents and dispute reading), Visa Intelligent Commerce via Airi (one passkey approval), Airwallex sandbox, T:0 sandbox.

What is labelled rather than live:
- **Globex's and Initech's books** are the stand-in (`fixtures/standin-books.json`): Globex has paid 3 invoices on time, Initech has INV-3002 ($400) overdue. T:0 has no matching customers and this key can read records and post journal entries but cannot create records (`403 CAPI72`). Acme's books are real T:0 records.
- **The Airwallex deposit** is a sandbox simulation (the sandbox cannot receive stablecoins); quote and conversion are real sandbox calls.
- **The statement's due time is compressed**: the orders are due in 10 days; the statement mandate opens about 75 s after it is issued and closes 5 min later, so the video can show both refusals and the collection.
- **The stale units in the dispute are set by the script** (it marks 10% of the disputed order as flagged by delivery QA). The model reads the email; the credit comes from that QA count, not from the email's "all units".
- **Globex's card is the same Airi test card** Acme used on 2026-11-09 (one card is enrolled).
- **Globex's card statement hash in this run is a placeholder** (`0xrmwaklnvkg1`), not a hash of the order. The script now uses the order's SHA-256 (as statements do); that fix has not been re-run with a passkey.
- **Initech** has no Metal account or mandate (placeholder address); it exists to show the books and the attacker being refused.
- **Acme's testnet balance** was raised above the faucet's 100 USDZ ceiling with `scripts/top-up-buyer.ts` (helper-account pulls `0xe8757220…bee3`, `0xb25e7c5e…f0fd` before this run).
